# Подготовка к контрольной работе

## Когда я выберу rebase, а когда merge? Почему?
Rebase — для своей локальной feature-ветки, которую ещё никто не забрал: перед Pull Request я переношу её на свежий main и получаю линейную историю без лишних merge-коммитов.
Merge — когда вливаю готовую ветку в общий main или работаю с веткой, которую уже используют коллеги: merge не переписывает существующие коммиты и сохраняет факт параллельной разработки.

## Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?
У коммитов изменятся хеши, и моя история разойдётся с историей коллег. Чтобы отправить её, придётся делать push --force, который затрёт чужие коммиты на сервере, а у коллег при следующем pull появятся дубли коммитов и конфликты.

## Зачем нужен multi-remote и в каких реальных сценариях он применяется?
Multi-remote позволяет одному локальному репозиторию работать с несколькими серверами. Сценарии: зеркало на GitLab как резервная копия GitHub; fork в OpenSource (origin — свой fork, upstream — оригинальный проект, из которого подтягиваются обновления); перенос проекта между платформами без потери истории; отдельный remote для деплоя на сервер.
