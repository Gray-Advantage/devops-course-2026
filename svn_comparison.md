# Git vs SVN

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?
В Git ветка — это просто указатель на коммит (файл с 40-символьным хешем в `.git/refs/heads`). Создание ветки ничего не копирует, выполняется мгновенно и локально, а переключение меняет только те файлы, которые отличаются.

В SVN ветка — это копия каталога в репозитории (`svn copy trunk branches/feature`). Копирование на сервере ленивое, но с веткой приходится работать как с отдельным деревом: её нужно выкачать или переключить рабочую копию через сеть, а слияние обратно в trunk долго было ручным и до сих пор опирается на свойство `svn:mergeinfo`. Поэтому в SVN ветки заводят редко — это дорого по времени и по процессу.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?
Нет. Коммит в SVN — это отправка изменений на центральный сервер: только там хранится история и номера ревизий. Офлайн можно лишь редактировать файлы рабочей копии и сравнивать их с базовой версией (`svn diff`, `svn revert` работают по копии в `.svn`). Коммитить, смотреть полный лог и создавать ветки без сервера нельзя. В Git вся история лежит локально, поэтому коммиты, ветки и лог доступны без сети, а на сервер изменения уходят позже через `git push`.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?
- **Большие бинарные файлы** (игровые ассеты, CAD-модели, макеты): SVN не заставляет каждого хранить всю историю бинарников и умеет блокировать файл (`svn lock`), чтобы двое не правили одну несливаемую модель одновременно.
- **Частичный checkout**: из огромного репозитория можно выкачать только нужный подкаталог.
- **Строгие права по путям**: доступ настраивается на уровне отдельных каталогов, что удобно для закрытых подразделений.
- **Сквозные номера ревизий** (r1542) удобны для нумерации сборок и аудита.
- **Legacy-проекты** в банках и госсекторе, где инфраструктура и регламенты построены вокруг SVN и миграция дороже, чем выгода от неё.
